The send state machine

A proposed design for how a logos-delivery node sends a message. send returns the message hash at once and refuses what the node cannot send. Each accepted send then runs through a state machine that is data, for 20 s from its timestamp.

Drive a send

Pick a scenario and press Next step. Each press is one report, and the send moves along one arrow. Drive it yourself lets you pick the node and choose each report.

The shape of a send

A round tries each transport of the node one time. When a peer takes the message, a reliable send waits for a Store node, and each other send ends in Propagated. A send over mix on a reliable node ends in MixDelivered, which the picture leaves out.

How to read a plan line

The simulator prints each arrow in this notation. The code builds the plan with the same operators, so a line in the source and a line in a log read the same.

The plan, PR by PR

PR of the trainWhat it does to the plan
1. Model each send as a state machineAdds the plan as data, with its builder and its tests. No send runs on it yet.
2. Run each send as a state machineThe send service runs each send on the plan.
3. Return the message hash from sendNo change.
4. Refuse a send over the rate-limit budget in sendAdmission becomes Prove. The wait for budget leaves the plan, with ParkedTooLong, EphemeralDropped and ReportQueued.
5. Refuse a message that is too large in sendOn a node with mix required, Prove no longer reports ProofSizeUnknown and TooLargeForMix.
6. Keep an unanswered mix send off the plain pathAdds MixNoReply, MixUnanswered and MarkMixUnanswered. On a node with mix, two arrows come in and one goes out.
7. Count a delivery window of 20 s from the message timestampProve can report WindowElapsed.
8. Give MessageErrorEvent the kind of the failureNo change. The end state gives the kind.
